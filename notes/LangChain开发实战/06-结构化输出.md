# 06 结构化输出

> 来源：`尚硅谷-06-结构化输出.pdf`。本章示例按当前项目的 LangChain 版本整理。

## 学习目标

- 理解为什么业务系统不能只接收自然语言
- 掌握 Pydantic、TypedDict、JSON Schema 和 dataclass 四种结构描述方式
- 使用 `with_structured_output()` 获得可直接使用的 Python 数据
- 理解 `method`、`include_raw` 和解析失败处理
- 知道什么时候使用输出解析器作为兼容方案

## 1. 为什么需要结构化输出

普通模型返回的是自然语言字符串：

```text
张三的邮箱是 zhangsan@example.com，电话是 13800000000。
```

业务代码真正希望拿到的是稳定字段：

```json
{
  "name": "张三",
  "email": "zhangsan@example.com",
  "phone": "13800000000"
}
```

结构化输出主要解决三个问题：

1. **字段稳定**：调用方知道有哪些字段以及字段类型。
2. **便于校验**：格式、范围、枚举和必填项可以在运行时检查。
3. **便于集成**：结果可以直接传给数据库、接口和后续 Runnable。

它不能保证内容事实正确。Schema 只能约束“形状”，不能自动消除幻觉。

## 2. 四种 Schema

| 方式 | 返回值 | 运行时校验 | 适合场景 |
|---|---|---|---|
| Pydantic | `BaseModel` 对象 | 强 | Python 项目首选、字段约束复杂 |
| TypedDict | `dict` | 默认不校验 | 轻量类型提示、只需要固定键 |
| JSON Schema | `dict` | 依赖模型和集成 | 跨语言协议、已有 JSON 规范 |
| dataclass | dataclass 对象或字典，依集成而定 | 基础 | 领域对象简单、已有 dataclass |

### 2.1 Pydantic

所有 Pydantic Schema 都继承 `BaseModel`：

```python
from typing import Literal

from pydantic import BaseModel, Field


class CustomerIssue(BaseModel):
    """从客服消息中提取的问题。"""

    name: str = Field(description="客户姓名")
    phone: str | None = Field(default=None, description="联系电话")
    issue: str = Field(description="客户遇到的问题")
    urgency: Literal["低", "中", "高"] = Field(description="紧急程度")
```

`Field` 可以表达：

- 字段说明：`description`
- 默认值：`default`
- 长度限制：`min_length`、`max_length`
- 数值范围：`gt`、`ge`、`lt`、`le`
- 正则格式：`pattern`

```python
class Product(BaseModel):
    name: str = Field(min_length=2, description="产品名称")
    price: float = Field(gt=0, description="产品价格")
    rating: int = Field(ge=1, le=5, description="1 到 5 分")
```

Pydantic 还支持嵌套结构：

```python
class Address(BaseModel):
    city: str
    district: str | None = None


class Company(BaseModel):
    name: str
    address: Address
```

字段描述应该告诉模型“字段代表什么”，不要只重复字段名。

### 2.2 TypedDict

`TypedDict` 用类型提示描述字典固定有哪些键：

```python
from typing import Annotated, NotRequired, TypedDict


class Movie(TypedDict):
    title: Annotated[str, "电影名称"]
    year: Annotated[int, "上映年份"]
    director: NotRequired[Annotated[str, "导演姓名"]]
```

返回结果通常是普通字典：

```python
{
    "title": "盗梦空间",
    "year": 2010,
    "director": "克里斯托弗·诺兰",
}
```

关键区别：`TypedDict` 主要服务于静态类型检查，Python 运行时不会像 Pydantic 一样自动执行完整校验。因此它更轻，但不适合依赖严格校验的业务入口。

### 2.3 JSON Schema

JSON Schema 是跨语言的结构描述协议：

```python
movie_schema = {
    "title": "movie",
    "description": "电影基本信息",
    "type": "object",
    "properties": {
        "title": {
            "type": "string",
            "description": "电影名称",
        },
        "year": {
            "type": "integer",
            "description": "上映年份",
        },
        "director": {
            "type": "string",
            "description": "导演姓名",
        },
    },
    "required": ["title", "year"],
}
```

适用场景：

- 前后端或多语言服务共用同一份协议
- 已经存在 OpenAPI / JSON Schema 定义
- 需要直接控制底层 Schema

缺点是代码较长，维护成本通常高于 Pydantic。

### 2.4 dataclass

```python
from dataclasses import dataclass, field


@dataclass
class Movie:
    title: str = field(metadata={"description": "电影名称"})
    year: int = field(metadata={"description": "上映年份"})
    director: str | None = field(
        default=None,
        metadata={"description": "导演姓名"},
    )
```

dataclass 是 Python 标准库的数据对象。它适合简单领域模型，但字段校验能力不如 Pydantic。不同模型集成和 LangChain 版本对 dataclass 的支持细节可能不同，项目接入时应做真实调用验证。

## 3. `with_structured_output()`

最常用的结构化输出入口是：

```python
structured_model = model.with_structured_output(CustomerIssue)

result = structured_model.invoke(
    "王小明反馈订单一直没发货，非常着急，电话是 13800000000"
)

print(type(result))
print(result.name)
print(result.urgency)
```

执行过程可以理解为：

```text
Schema
  -> LangChain 转换为模型能理解的结构声明
  -> 模型按结构生成结果
  -> LangChain 解析结果
  -> Pydantic 校验
  -> 返回 CustomerIssue 对象
```

如果传入 Pydantic 类型，成功时通常返回对应对象；传入 TypedDict 或 JSON Schema 时通常返回字典。

### 3.1 它仍然是 Runnable

`with_structured_output()` 返回的对象实现了 Runnable 接口，因此可以直接调用：

```python
result = structured_model.invoke(text)
results = structured_model.batch(texts)
```

也可以放进 LCEL：

```python
chain = prompt | model.with_structured_output(CustomerIssue)
result = chain.invoke({"message": user_message})
```

## 4. `method` 参数

部分模型集成允许显式指定结构化输出的实现方式：

```python
structured_model = model.with_structured_output(
    CustomerIssue,
    method="json_schema",
)
```

常见模式如下，具体支持情况以模型提供商和当前集成为准：

| 模式 | 原理 | 特点 |
|---|---|---|
| `json_schema` | 使用提供商原生 Structured Output | 约束通常最强，但模型必须支持 |
| `function_calling` | 把 Schema 转成工具/函数调用 | 兼容面较广 |
| `json_mode` | 要求模型输出合法 JSON | 只保证 JSON 时，字段约束可能较弱 |

选择原则：

```text
提供商原生支持并验证通过 -> json_schema
仅稳定支持 Tool Calling -> function_calling
只支持 JSON 输出模式 -> json_mode
都不支持 -> Prompt + OutputParser 兼容方案
```

“模型能输出 JSON”不等于“模型原生支持严格 JSON Schema”。是否支持必须通过提供商文档和真实测试确认。

## 5. `include_raw=True`

默认情况下，结构化调用只返回解析结果。需要查看原始消息、Token 用量或解析异常时，可以开启：

```python
structured_model = model.with_structured_output(
    CustomerIssue,
    include_raw=True,
)

result = structured_model.invoke("客户张三说订单未发货")
```

返回值通常包含：

```python
{
    "raw": AIMessage(...),
    "parsed": CustomerIssue(...),
    "parsing_error": None,
}
```

三个字段的含义：

| 字段 | 含义 |
|---|---|
| `raw` | 模型返回的原始 `AIMessage` |
| `parsed` | 成功解析后的对象或字典 |
| `parsing_error` | 解析或校验异常，成功时为 `None` |

```python
if result["parsing_error"] is not None:
    raise ValueError("模型结果无法解析") from result["parsing_error"]

issue = result["parsed"]
usage = result["raw"].usage_metadata
```

生产环境中 `include_raw=True` 很适合调试和观测，但日志中仍需脱敏。

## 6. 解析失败如何处理

常见失败包括：

- 返回的不是合法 JSON
- 缺少必填字段
- 字段类型不匹配
- 枚举值不合法
- 数值超出范围
- 模型或兼容接口不支持所选 `method`

推荐顺序：

```text
记录脱敏后的错误类型
-> 判断是否属于可重试错误
-> 最多有限次数重试
-> 必要时切换 method 或模型
-> 返回明确的业务失败
```

不要无限要求模型“重新输出一次”，也不要在校验失败后直接使用未经验证的原始字符串。

## 7. Output Parser 兼容方案

模型没有 `with_structured_output()`，或者兼容接口实现不完整时，可以使用输出解析器：

```python
from langchain_core.output_parsers import PydanticOutputParser
from langchain_core.prompts import ChatPromptTemplate

parser = PydanticOutputParser(pydantic_object=CustomerIssue)

prompt = ChatPromptTemplate.from_messages(
    [
        ("system", "从用户消息中提取客服问题。\n{format_instructions}"),
        ("human", "{message}"),
    ]
).partial(format_instructions=parser.get_format_instructions())

chain = prompt | model | parser
```

这里发生了三件事：

1. `get_format_instructions()` 生成结构说明。
2. `partial()` 提前固定这段说明，调用时只需传 `message`。
3. `parser` 是 Runnable，负责把模型文本解析为 `CustomerIssue`。

这种方式主要依赖提示词，约束通常弱于提供商原生 Structured Output，因此应作为兼容方案，而不是有原生能力时的第一选择。

## 8. Schema 设计原则

### 8.1 字段最少化

只定义业务真正需要的字段。字段越多，模型越容易漏填或互相混淆。

### 8.2 约束明确

优先使用枚举和范围，而不是在描述里写模糊要求：

```python
urgency: Literal["低", "中", "高"]
```

比下面更容易验证：

```python
urgency: str  # 请输出合理的紧急程度
```

### 8.3 区分“未知”和“空值”

缺少信息时使用可选字段：

```python
email: str | None = None
```

不要要求模型编造默认邮箱或电话。

### 8.4 二次业务校验

结构正确不等于业务合法：

```text
Pydantic 校验通过
-> 权限校验
-> 资源归属校验
-> 数据库约束
-> 业务状态校验
-> 执行业务操作
```

## 9. 完整示例

```python
from typing import Literal

from langchain.chat_models import init_chat_model
from pydantic import BaseModel, Field


class Review(BaseModel):
    product: str = Field(description="产品名称")
    rating: int = Field(ge=1, le=5, description="1 到 5 分")
    sentiment: Literal["positive", "neutral", "negative"]
    pros: list[str] = Field(default_factory=list)
    cons: list[str] = Field(default_factory=list)


model = init_chat_model(
    model="openai:your-model",
)

review_model = model.with_structured_output(Review, include_raw=True)
result = review_model.invoke(
    "这款耳机降噪很好，佩戴也舒服，但是价格偏高，我给 4 分。"
)

if result["parsing_error"]:
    raise RuntimeError("评论解析失败") from result["parsing_error"]

review = result["parsed"]
print(review.model_dump())
```

## 总结

```text
Pydantic：强校验，Python 业务项目首选
TypedDict：轻量字典类型提示
JSON Schema：跨语言、底层协议
dataclass：标准库数据对象
with_structured_output：首选入口
method：选择原生 Schema、Tool Calling 或 JSON Mode
include_raw：同时保留原始消息、解析结果和异常
OutputParser：无原生能力时的兼容方案
```

结构化输出负责把模型结果变成可靠的数据入口；事实正确性、权限和业务合法性仍由知识、工具与业务代码负责。
