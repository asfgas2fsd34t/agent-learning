# 10 概念问答集

> 来源：Spring AI 学习过程中的概念辨析问答（配套官方文档 1.1.x）。

本章汇总学习过程中"卡壳再讲透"的概念，按主题归类，方便回查。

## 1. Advisor 相关

### Q1：BaseAdvisor 和 Advisor 什么区别？

- `Advisor` 根接口只有 `getName()` + `getOrder()`，是"身份"，不干活
- `BaseAdvisor` 是**自动挡**基类：实现 `before`/`after` 两个钩子即可，call/stream 自动适配；流式的 after 只在流结束（finish reason）时回调一次
- 手工挡是 `CallAdvisor`/`StreamAdvisor`：自己写 `adviseCall`/`adviseStream`，控制 `chain.next`、逐片处理流

### Q2：`.advisors(a -> a.param(ChatMemory.CONVERSATION_ID, id))` 什么意思？

`a.param(key, value)` 给本次调用的 Advisor 传运行时参数，存在 `AdvisedRequest.adviseContext()` 里。`ChatMemory.CONVERSATION_ID` 是记忆 Advisor 约定的 key——告诉它这次属于哪个会话。挂了记忆 Advisor 后**每次必传**，否则会话串台。

### Q3：预设 Advisor 好不好用，是不是大部分要自定义？

优先用预设（记忆、日志、RAG、工具循环都有现成的）。要自写的典型是公司特有横切逻辑：敏感词合规、质量门重问、审计灰度。约 80% 装配 + 20% 自定义。

### Q4：完整系统中哪些放切面、哪些手写？

对所有模型调用统一生效的横切逻辑（记忆、日志、敏感词、重试、RAG 注入）→ Advisor；与业务流程强绑定的（分支决策、事务入口、返回码）→ 手写业务代码。

## 2. Prompt / 返回值相关

### Q5：generations 是什么？

`ChatResponse.getResults()` 返回 `List<Generation>`——一次调用的"候选回答列表"。每个 `Generation` = `AssistantMessage`（模型说的话）+ `ChatGenerationMetadata`（finishReason 等）。`getResult()` = 取第一条。多数情况只有 1 条；采样多候选（n>1）时会有多条。

### Q6：getResults() 返回什么？

同上：`List<Generation>`。取文本：`response.getResult().getOutput().getText()`。

## 3. Java 语言相关

### Q7：什么是 Java 的泛型擦除？

泛型只在编译期检查，编译后类型参数被擦掉：`List<ActorFilms>` 和 `List<String>` 运行时都只是 `List`。所以不能写 `entity(List<ActorFilms>.class)`。对策是 `new ParameterizedTypeReference<List<ActorFilms>>() {}`——匿名子类把泛型签名**保留在字节码里**，运行时反射可读，等于"骗过"擦除。

## 4. 记忆相关

### Q8：memory 和 history 什么区别？我们加的 advisor 是哪种？

- **ChatMemory**：窗口化的模型上下文（下一次调用带哪些消息），超窗会丢
- **ChatHistory**：全量对话账本，审计/回放用，要用 Spring Data 另存

`MessageChatMemoryAdvisor` 挂的是 **memory**。对话要"留档"得自己另存 history。

### Q9："就是模型上下文呗类似"——对吗？

对。memory ≈ 下次请求送给模型的上下文内容。区别是：模型窗口是硬件/服务限制（如 128K token），memory 是应用层裁剪策略（如最近 20 条），memory 必须装进模型窗口里。

### Q10：能不设窗口大小吗？LLM 到窗口大小不是会自动压缩吗？

**不会自动压缩**——这是最常见的误解。超窗会报错（超过 max context length）或被截断，压缩/裁剪完全是应用层的事。所以 `maxMessages`（默认 20）必须设，它是防止无限增长的闸门。想要"压缩"效果要自己实现摘要式记忆（见 08 章第 6 节 SummarizingChatMemory）。

### Q11：ChatMemoryRepository 需要自定义吗？

多数不需要。官方有 Jdbc/Memory 等实现；摘要只是存成 SystemMessage，存储层无感知。只有存储介质官方没有（自研缓存、加密存储）才自己实现接口。

### Q12：用 PG 做 repository 行不行？

行。`JdbcChatMemoryRepository` + `PostgresChatMemoryRepositoryDialect`，表 `SPRING_AI_CHAT_MEMORY` 官方 schema 直接用（见 08 章第 5 节）。

### Q13：多个数据源怎么办？

自动配置拿的是 @Primary 的 DataSource/JdbcTemplate——业务库和记忆库分开时会拿错。手动定义 `ChatMemoryRepository` Bean 钉住记忆库的 JdbcTemplate，`@ConditionalOnMissingBean` 让自动配置让位（见 08 章第 7 节）。

### Q14：是不是还得自定义 businessMemoryRepository？

不存在这种东西。记忆 repository **只有一个**。业务数据走你自己的 DAO/JPA——"业务库读写"和"记忆"是两码事，别混。

## 5. 工具调用相关

### Q15：模型能直接执行工具吗？

不能。模型只输出"我想调用 X 工具、参数是 Y"的请求（tool_calls），执行由你的应用完成——这正是安全边界：模型碰不到你的系统，权限收敛在执行账号。

### Q16：ToolContext 和工具参数什么区别？

工具参数会进模型（Schema 发给模型、值由模型填）；ToolContext 是**应用侧注入**的 Map（userId、租户、traceId），不发给模型，模型看不到也伪造不了——多租户鉴权放这里。

## 6. "上下文"辨析

### Q17："上下文"到底是什么？（模型上下文 / ToolContext / MCP 请求上下文）

"上下文"= 调用发生时携带的**额外信息或能力**，不是业务数据本身。学过的内容里出现过四种：

1. **模型上下文（context window）**：一次请求发给 LLM 的全部内容（system + 历史 + 用户输入），即"prompt 的另一个说法"。ChatMemory 管的就是它（08 章）。
2. **ToolContext**（09 章）：调用工具时应用侧注入的数据（userId、租户），不发给模型，工具方法里取用。
3. **MCP 请求上下文**（14 章）：`McpSyncRequestContext` / `McpTransportContext`——框架自动注入到 `@McpTool` 方法里的"本次调用的会话对象"，里面是原始请求（progressToken）、连接能力开关（elicit/sample）和方便方法（info/progress/ping）。类比 Spring MVC 的 `HttpServletRequest`。
4. **MCP 协议名里的 Context**：Model Context Protocol = "给模型提供外部上下文（工具、资源）的协议"，此 context 指模型可用的外部能力。

注意 ToolContext 与 MCP 请求上下文会在 MCP 场景相遇：客户端的 ToolContext 经 `ToolContextToMcpMetaConverter` 转成 MCP 调用元数据（13 章），server 侧用 `McpSyncRequestContext`/`McpMeta` 读到。

### Q18：McpSyncRequestContext 是 client 传进来的吗？

不是。客户端传过来的只是 **JSON-RPC 请求数据**（工具参数、progressToken、`_meta` 元数据）；`McpSyncRequestContext` 是**服务端框架**收到请求后自己构造、注入到 `@McpTool` 方法里的对象——它"包裹"了两样东西：客户端传来的请求数据 + 服务端持有的回连会话（用来给客户端发 info/progress/ping）。类比 `HttpServletRequest`：HTTP 请求是浏览器发的，但 request 对象是 Tomcat 造的。框架注入的特殊参数都遵循这个模式（自动注入、不进 JSON Schema）。客户端侧没有这个对象，客户端对应的是 Customizer/handler 体系。

### Q19：什么时候会用这个 context？

**只有工具需要"和调用方互动"时才用**——约 80% 的纯查询工具用不上。典型场景：

1. **长任务进度**：客户端带了 progressToken 时，用 `context.progress(...)` 上报百分比（导出报表、批量处理）
2. **回传日志**：`context.info(...)` 把结构化日志发给客户端展示/排查
3. **防断线**：长操作里 `context.ping()` 保活
4. **向用户要补充信息**：`context.elicit(...)`（下单缺座位号，经客户端问用户）——仅 Stateful
5. **借客户端调 LLM**：`context.sample(...)`（服务端没有 API Key 也能摘要/分类）——仅 Stateful
6. **读请求元数据**：`context.request().progressToken()` / `requestMeta()`（多租户 userId、traceId 从客户端 ToolContext 转来）

判断法：工具是"一问一答"就别加 context（保持 Schema 干净）；需要中途说话/要东西/看元数据才加。Stateless 部署用不了它（会被过滤），只读元数据可改用更轻的 `McpMeta`。

### Q20：client 怎么拿到 server 的 info/progress？

两侧是**通知（notification）机制**：server 调 `context.info()/progress()` → 框架转成 LoggingMessageNotification / ProgressNotification 沿会话推给 client → client 事先注册的处理器接收。两种收法：

1. **编程式**：`McpSyncClientCustomizer` 里 `spec.loggingConsumer(n -> ...)`、`spec.progressConsumer(p -> ...)`（13 章 7.1 示例）
2. **声明式**：客户端注解 `@McpLogging(clients = "server名")`、`@McpProgress` 标注方法自动注册

⚠️ 进度有前提：**client 发起调用时要带 progressToken**（Spring AI 的玩法是 `.toolContext(Map.of("progressToken", "tok"))`，经 Converter 转进 MCP meta），server 侧 `context.request().progressToken()` 拿到后 `progress()` 才发得出、client 才收得到。info 没有这个门槛，注册了 consumer 就能收。

### Q21：为什么进度需要 token？

因为进度通知是**按次调用的订阅制流**，token 就是这次调用的关联凭证（correlation id），解决三件事：

1. **关联**：同一连接上可能有多个并发调用（导出、搜索同时跑），进度通知推回来时靠 token 分清"这是哪个任务的进度"，路由到对应的 UI 进度条
2. **显式订阅**：token 表达"我这次调用要进度"。毫秒级的调用发进度纯属噪音和开销，不是所有客户端都能处理进度——所以默认不发，带了 token 才发
3. **双向确认**：server 靠 `request().progressToken()` 判断对方订没订阅，没 token 就不用浪费通知

类比外卖订单号：进度推送必须挂在订单号上，多笔订单才不会串。token 随请求 `_meta` 过去，随每条 ProgressNotification 传回，就是 MCP 规范的 `notifications/progress` 机制。

### Q22：这不是一次请求的长链接吗？是类似多路复用？

对，就是多路复用。精确说：**连接是"一对 client-server 一条会话"，不是一请求一条**；多个调用在同一条会话上并发交错跑，靠三层归属拆分（demux）：

| 消息 | 配对机制 | 归属 |
|------|---------|------|
| JSON-RPC 请求/响应 | 消息里的 `id` | 请求级 |
| ProgressNotification | `progressToken`（请求 `_meta` 里声明） | 请求级 |
| LoggingMessageNotification（info） | 无 id 无 token | **会话级**，谁注册谁收 |

这直接解释了上一问：info 之所以不用 token，因为它本来就是会话级旁路广播；进度是请求级状态流，才需要凭证。反证是 STATELESS 协议：无会话 = 每次调用独立 HTTP 请求 = 没有多路复用也没有回推通道——所以双向能力（progress/sample/elicit）全部不可用，原因就在"没有会话"。

类比：HTTP/2 的 stream 多路复用、gRPC、WebSocket、数据库连接池复用——同一根管子上跑多个逻辑流，各流靠 id/凭证拆开。

## 7. 选型与 Agent 形态

### Q23：什么时候用 Spring AI，什么时候用 Spring AI Alibaba？

不是二选一——Spring AI Alibaba 是构建在 Spring AI **之上**的生态扩展层（ChatClient/Advisor/@Tool 这套 API 全来自 Spring AI）。决策是"要不要叠 Alibaba 层"：

| 场景 | 选择 |
|------|------|
| OpenAI/Claude/Gemini/Ollama | 纯 Spring AI |
| DeepSeek/Qwen 等国产模型 | 纯 Spring AI 够（OpenAI 兼容端点直连） |
| 通义全家桶/百炼平台/阿里云组件 | 叠加 Spring AI Alibaba |
| 多 Agent/工作流图编排（Graph） | Alibaba Graph 模块 |
| 想跟官方新特性、求稳 | 纯 Spring AI（Alibaba 稳定线钉在 Spring AI 1.1.2，2.0 线仅 M1 里程碑） |

原则：**底座永远 Spring AI，Alibaba 当插件按需引**——学标准 API 不会被锁定。

### Q24：实际项目都需要 Graph 吧？至少要 ReAct 循环，Spring AI 不支持吧？

ReAct 和 Graph 是两个东西。**ReAct：Spring AI 完全支持且开箱即用**——工具循环就是 ReAct（Thought→Action→Observation 循环），09 章的三种执行模式都是它：框架托管的 while 循环、ToolCallAdvisor、用户自控 `while (hasToolCalls())`。模型的 tool_calls 就是 Thought+Action，ToolMessage 回传就是 Observation。

**Graph：Spring AI 核心确实没有图编排 API**（没有 LangGraph 那种 StateGraph/节点/边/检查点）。但"实际项目都需要 Graph"不成立——问答、RAG、工具 Agent（ReAct）覆盖大多数生产场景，多步显式控制流（分支/并行/人工中断/多 Agent 协作）才需要 Graph。需要时的选项：Spring AI Alibaba Graph、自研状态机（服务代码 + 记忆）、Spring 生态工作流引擎（Camunda/Flowable）。

### Q25：多模型多个 ChatClient 时为什么要用 ChatClientBuilderConfigurer？

场景：一个应用接多个模型（OpenAI + Anthropic），要建多个 ChatClient。**错误写法**是 `@Bean ChatClient x(OpenAiChatModel m) { return ChatClient.create(m); }`——`create()/builder()` 是"裸造"，绕过了自动配置的 `ChatClient.Builder`，后果是**观测性（tracing/metrics）丢失、`ChatClientBuilderCustomizer` 全被忽略**。

正确做法：注入 `ChatClientBuilderConfigurer`（自动配置内部的"装配器"），把裸 builder 交给 `configurer.configure(builder).build()`，它会把所有 Customizer + 观测性装回去。多个 ChatModel bean 还会让自动配置注入歧义——给常用那个标 `@Primary`（和 08 章多数据源同一个坑同一个解法）。单模型场景零配置，不用碰这套。注意：这是 **2.0 文档**的写法（代码里 `ToolCallingAdvisor.Builder` 是 2.0 命名）。

### Q26：什么叫"绕过了自动配置的 bean"？

**bean = 由 Spring 容器创建和管理的对象；自动配置 = Spring Boot 启动时预装的"装配线"，帮你把一批现成对象造好（且造的时候就把周边零件装上：观测性埋点、所有 Customizer），放进容器待领。**

"绕过"= 你不从容器领现成的，而是自己调 `ChatClient.create()`/`builder()` 造一个。自己造的对象**没经过那条装配线**——零件没装；Spring 也不会事后补，因为它只在启动装配阶段动手，你自己造的对象它看不见。注意 `@Bean` 方法返回它只是"登记给 Spring 管理生命周期"，**不等于经过了自动配置的装配**——零件是在"造的过程"中装的，不是在"登记"时装的。

类比：从 4S 店提整车（带保险、贴膜、检测）vs 自己买零件拼一台能开的车——`@Bean` 只是把拼好的车登记到你名下，4S 店不会给它补装保险。解法 `ChatClientBuilderConfigurer` 就是"把拼好的车送回装配线补装零件"。
