# 11. 流式执行

流式执行让调用方在图结束前持续获得状态更新、模型 Token、任务事件或业务进度。它主要改善交互延迟和可观测性，不会改变图的控制流。

## 11.1 stream 与 astream

同步代码使用 `stream()`：

```python
for chunk in graph.stream(
    initial_state,
    config=config,
    stream_mode="updates",
):
    print(chunk)
```

异步服务使用 `astream()`：

```python
async for chunk in graph.astream(
    initial_state,
    config=config,
    stream_mode="updates",
):
    await send_to_client(chunk)
```

生产 Web 服务优先使用异步流，并在客户端断开时取消下游任务或停止继续推送。

## 11.2 stream_mode

| 模式 | 输出内容 | 适用场景 |
| --- | --- | --- |
| `values` | 每个超步后的完整 State | 查看状态演进 |
| `updates` | 各节点产生的增量更新 | UI 展示阶段结果 |
| `messages` | 模型消息分块和元数据 | Token 级聊天输出 |
| `custom` | 节点或 Tool 主动写出的数据 | 业务进度、百分比 |
| `checkpoints` | 检查点事件 | 持久化和中断调试 |
| `tasks` | 任务开始、结果、错误等事件 | 节点级观测 |
| `debug` | 更完整的检查点和任务调试信息 | 本地排错 |

### values 与 updates

假设节点只返回 `{"status": "done"}`：

- `updates` 只输出该节点的增量更新。
- `values` 输出合并后的完整 State。

State 很大时，前端通常使用 `updates`，避免反复传输完整状态。

### messages

```python
from langchain.messages import AIMessageChunk


async for message_chunk, metadata in graph.astream(
    {"messages": [("user", "解释 LangGraph")]},
    stream_mode="messages",
):
    if isinstance(message_chunk, AIMessageChunk):
        print(message_chunk.content, end="", flush=True)
```

`metadata` 可用于判断消息来自哪个节点、模型或运行标签。不要假设每个 chunk 都是纯文本，消息还可能包含 Tool Call 分块或其他内容块。

### custom

节点可以主动发送业务进度：

```python
from langgraph.config import get_stream_writer


def process_documents(state: State) -> dict:
    writer = get_stream_writer()
    writer({"stage": "loading", "progress": 0.2})
    documents = load_documents()
    writer({"stage": "processing", "progress": 0.7})
    result = process(documents)
    writer({"stage": "done", "progress": 1.0})
    return {"result": result}
```

```python
for chunk in graph.stream(initial_state, stream_mode="custom"):
    print(chunk)
```

Tool 中可通过 `ToolRuntime.stream_writer` 写入同类事件。

### checkpoints、tasks 与 debug

这些模式适合开发和平台观测，不建议原样暴露给普通前端，因为其中可能包含 State、异常和内部节点信息。

- `checkpoints`：观察检查点创建和持久化内容。
- `tasks`：观察节点任务开始、完成、错误和中断。
- `debug`：信息最全，数据量也最大。

## 11.3 同时订阅多个模式

```python
async for mode, chunk in graph.astream(
    initial_state,
    stream_mode=["messages", "updates", "custom"],
):
    if mode == "messages":
        handle_message(chunk)
    elif mode == "updates":
        handle_update(chunk)
    else:
        handle_progress(chunk)
```

不同 LangGraph 版本和 `version="v1"/"v2"` 的封装格式可能不同。业务层应先把框架事件转换成自己稳定的事件协议，再发送给前端。

推荐业务事件：

```json
{
  "type": "token|progress|tool|result|error|interrupt",
  "run_id": "...",
  "sequence": 12,
  "data": {}
}
```

## 11.4 子图流

开启 `subgraphs=True` 可以看到子图内部事件：

```python
for namespace, chunk in graph.stream(
    initial_state,
    stream_mode="updates",
    subgraphs=True,
):
    print(namespace, chunk)
```

`namespace` 用于定位事件属于父图还是哪一层子图。嵌套结构较深时必须保留它，否则同名节点的事件无法区分。

## 11.5 astream_events

`astream_events()` 提供更通用的 Runnable 事件流，适合观察模型、Tool、Chain 和图节点的开始、流式输出与结束：

```python
async for event in graph.astream_events(
    initial_state,
    config=config,
    version="v2",
):
    if event["event"] == "on_chat_model_stream":
        chunk = event["data"]["chunk"]
        print(chunk.content, end="")
```

常见字段：

| 字段 | 含义 |
| --- | --- |
| `event` | 事件类型，例如 `on_chat_model_stream` |
| `name` | 产生事件的 Runnable 名称 |
| `run_id` | 当前运行 ID |
| `parent_ids` | 父运行链路 |
| `tags` / `metadata` | 调用配置中的标签和元数据 |
| `data` | 输入、输出或 chunk |

可以使用 `include_names`、`include_types`、`include_tags` 等参数过滤事件，避免把完整内部事件流发送给客户端。

### stream/astream 与 astream_events 的区别

| API | 关注点 |
| --- | --- |
| `stream/astream` | LangGraph State、消息、任务和自定义进度 |
| `astream_events` | 整个 Runnable 调用树的标准事件 |

聊天 UI 通常优先 `astream(..., stream_mode="messages")`；调试模型、Tool 和嵌套 Runnable 时使用 `astream_events()`。

## 11.6 流式执行底层理解

流式输出并不代表节点之间绕过 State：

```text
节点执行过程中产生 Token 或 custom 事件
-> 事件立即推送给调用方
-> 节点完成后返回 State 更新
-> Reducer 合并更新
-> 图进入下一超步
```

因此，客户端收到部分 Token 时，节点可能尚未成功提交最终 State。如果随后节点失败，UI 需要能显示失败或撤销“已完成”状态。

## 11.7 生产注意事项

1. 为每个事件添加 `run_id` 和递增序号，支持重连去重。
2. 区分“模型正在生成”和“业务操作已成功”。Token 输出不代表事务完成。
3. 处理客户端断开、背压、超时和取消。
4. 不把 `debug`、完整 State、系统 Prompt 和敏感 Tool 结果直接暴露给前端。
5. 限制事件大小和频率，过细的 Token/进度事件会增加网络与日志成本。
6. 中断、错误和最终结果使用明确事件类型。
7. 前端只展示允许公开的信息，权限过滤在服务端完成。
