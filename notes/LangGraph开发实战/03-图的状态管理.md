# 3. 图的状态管理

State 是 LangGraph 的数据总线。节点不直接互相调用并传参，而是读取 State、产生更新，再由运行时合并更新。

## 3.1 State 的三种定义方式

### TypedDict

最常用，类型清晰且运行开销低。

```python
from typing import TypedDict


class State(TypedDict):
    query: str
    answer: str
```

`TypedDict` 主要服务静态类型检查，本身不会在运行时强制校验值。

### dataclass

适合需要默认值或少量方法的状态对象。

```python
from dataclasses import dataclass, field


@dataclass
class State:
    query: str = ""
    tags: list[str] = field(default_factory=list)
```

可变默认值必须使用 `default_factory`。

### Pydantic BaseModel

适合需要运行时校验和复杂字段约束的输入边界。

```python
from pydantic import BaseModel, Field


class State(BaseModel):
    query: str
    retry_count: int = Field(default=0, ge=0, le=3)
```

Pydantic 更严格但开销更高。即使使用 Pydantic State，也不要假设每次内部状态更新都会自动完成全部业务校验；权限、金额和资源归属仍应在业务边界显式校验。

| 方式 | 优点 | 适用场景 |
| --- | --- | --- |
| TypedDict | 简单、低开销、生态示例最多 | 大多数图状态 |
| dataclass | 默认值和对象方法方便 | 状态有轻量行为 |
| Pydantic | 运行时校验强 | 外部输入、严格数据契约 |

## 3.2 Reducer：更新如何合并

State 的每个字段对应一个通道。节点返回更新后，Reducer 决定新值如何与旧值合并。

### 默认行为：覆盖

```python
class State(TypedDict):
    status: str
```

节点返回 `{"status": "done"}` 时，新值覆盖旧值。

如果同一超步中的多个并行节点同时更新没有 Reducer 的同一字段，通常会产生并发更新冲突。

### 自定义 Reducer：累加

```python
import operator
from typing import Annotated, TypedDict


class State(TypedDict):
    logs: Annotated[list[str], operator.add]
```

两个并行节点分别返回：

```python
{"logs": ["A 完成"]}
{"logs": ["B 完成"]}
```

Reducer 合并后得到：

```python
{"logs": ["A 完成", "B 完成"]}
```

Reducer 必须尽量满足结合律，最好也满足交换律，否则并行执行顺序可能影响结果。

### 消息 Reducer

消息不适合直接使用列表相加。`add_messages` 会按消息 ID 合并，同 ID 消息可以被替换或删除。

```python
from typing import Annotated, TypedDict
from langchain.messages import AnyMessage
from langgraph.graph.message import add_messages


class State(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
```

## 3.3 节点如何读取和更新 State

节点读取当前快照并返回部分更新：

```python
def classify(state: State) -> dict:
    category = "long" if len(state["query"]) > 50 else "short"
    return {"category": category}
```

推荐返回 `dict` 或 `Command(update=...)`，不要在节点中依赖原地修改 `state`。

### 绕过 Reducer

极少数场景需要直接覆盖带 Reducer 的字段，可以使用 `Overwrite`：

```python
from langgraph.types import Overwrite


def reset_logs(state: State) -> dict:
    return {"logs": Overwrite([])}
```

它表达“不要累加，直接把该通道替换为这个值”。一个超步内不能对同一通道产生多个 `Overwrite`。

## 3.4 多 Schema：控制状态边界

一个图可以区分：

- `state_schema`：内部完整状态。
- `input_schema`：调用方允许传入的字段。
- `output_schema`：图最终允许返回的字段。
- 节点 `input_schema`：单个节点能看到的状态视图。
- 私有字段：仅用于内部节点协作。

```python
class InputState(TypedDict):
    query: str


class OutputState(TypedDict):
    answer: str


class OverallState(InputState, OutputState):
    normalized_query: str
    internal_score: float


builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState,
)
```

多 Schema 的价值不是少写几个字段，而是防止内部实现泄漏到公共接口，并减少节点之间不必要的耦合。

## 3.5 预定义 State

### MessagesState

`MessagesState` 已定义带 `add_messages` Reducer 的 `messages` 字段：

```python
from langgraph.graph import MessagesState


class ChatState(MessagesState):
    user_id: str
    summary: str
```

适合对话、Tool Calling 和 Agent 图。

### AgentState

LangChain 的 Agent 运行时使用预定义 `AgentState`，通常包含消息以及结构化响应等 Agent 字段。使用 `create_agent()` 时优先使用框架提供的状态扩展方式，不要随意重定义内部字段语义。

## 3.6 State 设计原则

1. State 只保存跨节点需要共享的数据，节点局部变量不要放进去。
2. 字段名称表达业务语义，例如 `approved`、`tool_result`，不要使用 `temp1`。
3. 并行节点会共同更新的字段必须设计 Reducer。
4. 大对象和二进制内容保存引用或存储地址，不要直接塞进 State。
5. 敏感信息能不进入 State 就不进入，因为 Checkpointer、日志和 Trace 都可能保存它。
6. 公开输入、内部状态和最终输出应使用不同 Schema 隔离。
7. State 结构一旦持久化就会形成数据契约，生产升级需要考虑兼容和迁移。

## 3.7 常见误区

- **State 是全局变量**：它更接近每次图运行的版本化数据快照。
- **节点返回值就是下一个节点入参**：返回值先进入 Reducer，再形成后续节点看到的 State。
- **列表会自动追加**：没有声明 Reducer 时仍然是覆盖。
- **TypedDict 会自动校验**：它主要用于类型提示。
- **所有数据都放 State 最方便**：State 越大，持久化、序列化和调试成本越高。
