# 2. 图的基础构建与运行

## 2.1 构建图的四个步骤

一张最小状态图需要：定义 State、定义节点、连接边、编译。

```python
from typing import TypedDict

from langgraph.graph import END, START, StateGraph


class State(TypedDict):
    text: str
    result: str


def normalize(state: State) -> dict:
    return {"text": state["text"].strip()}


def summarize(state: State) -> dict:
    return {"result": f"已处理：{state['text']}"}


builder = StateGraph(State)
builder.add_node("normalize", normalize)
builder.add_node("summarize", summarize)
builder.add_edge(START, "normalize")
builder.add_edge("normalize", "summarize")
builder.add_edge("summarize", END)

graph = builder.compile()
```

节点通常只返回自己负责更新的字段，不必复制完整 State。

## 2.2 编译发生了什么

`builder` 是图定义，`compile()` 返回可运行的 `CompiledStateGraph`。编译阶段会检查节点和边，并把图转换为支持以下能力的 Runnable：

- `invoke()` / `ainvoke()`：单次同步或异步调用。
- `batch()` / `abatch()`：批量调用。
- `stream()` / `astream()`：流式获取执行过程。
- `get_state()`：配置 Checkpointer 后读取状态快照。

```python
result = graph.invoke({"text": "  LangGraph  ", "result": ""})
print(result)
# {'text': 'LangGraph', 'result': '已处理：LangGraph'}
```

编译前的 `StateGraph` 仍可继续添加节点和边；实际运行应使用编译后的 `graph`。

## 2.3 输入、更新与最终结果

一次调用的执行过程：

```text
调用输入
-> 写入初始 State
-> START 选择第一个节点
-> 节点返回部分更新
-> 更新合并进 State
-> 沿边继续执行
-> 到达 END
-> 返回最终 State
```

三个容易混淆的对象：

| 对象 | 含义 |
| --- | --- |
| `state` 参数 | 节点开始执行时看到的状态快照 |
| 节点返回值 | 本节点产生的状态更新，不是“下一节点参数” |
| `graph.invoke()` 返回值 | 图结束时的输出 State |

## 2.4 输入与输出 Schema

如果不单独声明，图的输入和输出都使用总 State。生产代码可以收窄公开边界：

```python
class InputState(TypedDict):
    text: str


class OutputState(TypedDict):
    result: str


class OverallState(InputState, OutputState):
    normalized: str


builder = StateGraph(
    OverallState,
    input_schema=InputState,
    output_schema=OutputState,
)
```

这样调用方只需提交 `text`，最终只得到 `result`，内部字段不会成为公共接口。

## 2.5 可视化

编译图可以导出 Mermaid：

```python
mermaid = graph.get_graph().draw_mermaid()
print(mermaid)
```

在支持图片渲染的环境中也可以生成 PNG：

```python
png = graph.get_graph().draw_mermaid_png()
with open("graph.png", "wb") as file:
    file.write(png)
```

可视化展示的是静态拓扑。运行时由 `Command`、`Send` 等动态产生的目标，需要通过节点的返回类型或 `destinations` 提供绘图提示。

## 2.6 常见问题

### 忘记连接 START

节点存在但不可达，图没有有效入口。

### 返回完整 State

会增加耦合，并可能覆盖其他节点更新。优先返回最小更新字典。

### 在节点里直接修改传入字典

不要依赖原地修改；显式返回更新，才能让 Reducer、持久化和调试行为保持清晰。

### 把 END 当成普通节点

`END` 是运行时终止标记，不需要 `add_node()`。条件路由可以直接返回 `END`，固定流程也可以通过边连接到 `END`。

## 2.7 最小验收清单

- State 字段能表达节点间真正需要共享的数据。
- 每个节点职责单一，只返回自己负责的更新。
- START 到 END 至少存在一条有效路径。
- 图编译后能用最小输入完成一次 `invoke()`。
- 对外输入和输出需要稳定时，单独定义 Schema。
