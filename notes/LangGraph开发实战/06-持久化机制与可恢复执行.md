# 6. 持久化机制与可恢复执行

持久化使 LangGraph 能保存某条执行线程的 State、下一步任务和运行元数据。它是多轮对话、中断恢复、故障恢复和 Time Travel 的基础。

## 6.1 核心概念

| 概念 | 含义 |
| --- | --- |
| Checkpoint | 某个超步边界上的状态和执行信息 |
| Checkpointer | Checkpoint 的读写实现 |
| `thread_id` | 一条会话或任务执行线的稳定 ID |
| `checkpoint_ns` | 父图、子图等层级的检查点命名空间 |
| `checkpoint_id` | 某个具体历史检查点的 ID |
| StateSnapshot | `get_state()` 暴露的开发者视图 |

三个 ID 的关系：

```text
thread_id：定位整条执行历史
checkpoint_ns：定位图层级
checkpoint_id：定位历史中的一个具体状态
```

`StateSnapshot` 常见字段：

- `values`：当时的 State。
- `next`：下一步待执行节点。
- `tasks`：待执行或已产生结果/错误/中断的任务。
- `config`：包含线程和检查点标识。
- `metadata`：来源、步骤等信息。
- `parent_config`：父检查点配置。
- `interrupts`：当前中断信息。

## 6.2 启用 Checkpointer

开发阶段可以使用内存实现：

```python
from langgraph.checkpoint.memory import InMemorySaver


checkpointer = InMemorySaver()
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "order-1001"}}
result = graph.invoke(initial_state, config=config)
```

同一个 `thread_id` 会沿用同一条历史；不同任务必须使用不同 ID。`InMemorySaver` 随进程结束而丢失，只适合测试和本地调试。

常见后端：

| 后端 | 适用场景 |
| --- | --- |
| InMemorySaver | 单进程开发和测试 |
| SqliteSaver | 轻量本地持久化 |
| PostgresSaver | 多进程、服务化生产环境 |
| Redis/MongoDB 实现 | 已有对应基础设施的系统 |

## 6.3 持久化时机与 durability

调用时可以设置写入策略：

```python
graph.invoke(
    initial_state,
    config=config,
    durability="sync",  # "async" / "exit"
)
```

| 模式 | 行为 | 权衡 |
| --- | --- | --- |
| `sync` | 检查点写入完成后再进入下一步 | 最可靠，延迟最高 |
| `async` | 写入与下一步执行并行 | 性能与可靠性的平衡 |
| `exit` | 图结束时统一持久化 | 最快，但中途崩溃可恢复进度最少 |

`durability` 不改变图的业务逻辑，只影响状态落盘时机。资金、订单等关键流程优先考虑 `sync`；普通对话通常可使用 `async`。

## 6.4 查看状态与历史

### 最新状态

```python
snapshot = graph.get_state(config)
print(snapshot.values)
print(snapshot.next)
print(snapshot.tasks)
```

### 完整历史

```python
history = list(graph.get_state_history(config))
for snapshot in history:
    print(snapshot.config["configurable"]["checkpoint_id"])
```

历史通常按从新到旧返回，具体使用时不要依赖隐含顺序，明确选择目标检查点。

### 指定检查点

```python
old_config = {
    "configurable": {
        "thread_id": "order-1001",
        "checkpoint_id": "目标检查点 ID",
    }
}
old_snapshot = graph.get_state(old_config)
```

子图场景还需要正确的 `checkpoint_ns`。

## 6.5 多轮对话

`MessagesState` 配合 Checkpointer 可以保存同一线程的消息：

```python
from langchain.messages import HumanMessage


config = {"configurable": {"thread_id": "user-42-session-7"}}

graph.invoke({"messages": [HumanMessage("我叫小王")]}, config=config)
result = graph.invoke(
    {"messages": [HumanMessage("我叫什么？")]},
    config=config,
)
```

Checkpointer 保存的是线程内短期状态，不等于跨线程长期记忆。长期记忆由 Store 管理，见第 07 篇。

## 6.6 失败后恢复

启用 Checkpointer 后，图在节点失败时保留已完成超步和部分任务写入。再次使用同一 `thread_id` 调用时，可以从可恢复位置继续，而不是无条件从头运行。

仍需注意：

- 一个节点可能被重新执行。
- 与失败节点并行的成功结果可以被保存并复用，但不要依赖未承诺的执行顺序。
- 外部副作用不能仅靠 Checkpointer 保证 exactly-once。
- 数据库写入、退款、发消息等操作仍要在业务服务实现幂等。

可恢复执行提供的是**状态与调度恢复**，不是分布式事务。

## 6.7 修改状态与 Time Travel

`update_state()` 可以基于某个检查点创建新的状态版本：

```python
updated_config = graph.update_state(
    old_snapshot.config,
    {"approved": True},
    as_node="review",
)
```

再从这个版本继续：

```python
result = graph.invoke(None, config=updated_config)
```

这会形成新的历史分支，而不是直接篡改旧检查点。常见用途：

- 修正某一步 State 后重放后续流程。
- 调试不同决策造成的结果。
- 人工审核后从指定位置继续。

Time Travel 不应被当成任意回滚外部世界。图状态回到过去，不代表已经发送的邮件、扣款或数据库写入自动撤销；这些需要补偿事务。

## 6.8 PostgreSQL 持久化

安装对应扩展后，可以使用 `PostgresSaver`：

```python
import os
from langgraph.checkpoint.postgres import PostgresSaver


db_url = os.environ["LANGGRAPH_DATABASE_URL"]

with PostgresSaver.from_conn_string(db_url) as checkpointer:
    checkpointer.setup()  # 初始化阶段执行，不要每次请求都执行
    graph = builder.compile(checkpointer=checkpointer)
    graph.invoke(
        initial_state,
        config={"configurable": {"thread_id": "task-1001"}},
    )
```

生产中应把 `setup()` 作为独立迁移步骤，并使用连接池或异步实现。数据库地址和密码放入环境变量或密钥服务。

`setup()` 通常创建四张核心表：

| 表 | 用途 |
| --- | --- |
| `checkpoints` | 状态快照、元数据和父检查点 |
| `checkpoint_writes` | 节点任务产生的通道写入 |
| `checkpoint_blobs` | 独立序列化的数据块 |
| `checkpoint_migrations` | Checkpointer 表结构迁移版本 |

`checkpoints` 常以 `(thread_id, checkpoint_ns, checkpoint_id)` 为联合主键。不要让业务代码直接依赖内部表字段完成状态更新，应通过 Checkpointer API 操作。

## 6.9 生产注意事项

1. `thread_id` 由应用服务生成并绑定当前用户/租户，不能直接信任模型或前端任意指定。
2. Checkpoint 可能包含完整消息和工具结果，应设置访问控制、加密、保留期限和删除机制。
3. 不要把大型文件、图片或不可序列化对象直接放入 State。
4. 图结构或 State Schema 升级后，旧 Checkpoint 可能不兼容，需要版本字段和迁移策略。
5. 数据库连接池、超时、容量、索引和备份要纳入运维。
6. 恢复流程必须配合业务幂等、状态查询和补偿逻辑。
7. 使用 `thread_id`、`checkpoint_id`、节点名和 Trace ID 串联日志。

## 6.10 Checkpointer 与业务数据库的边界

| 数据 | 建议位置 |
| --- | --- |
| 图执行进度、消息、待执行节点 | Checkpointer |
| 订单、退款、库存、权限 | 业务数据库 |
| 用户跨会话偏好和事实 | Store 或专用记忆库 |
| 大文件和原始文档 | 对象存储，State 只保存引用 |

Checkpointer 是工作流运行时存储，不应替代业务系统的事实来源。
