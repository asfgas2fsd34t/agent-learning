# 8. 中断

中断允许图暂停执行，把问题或待审核数据交给外部系统，等待人工或其他服务响应后从原线程继续。

典型场景：危险操作审批、人工修改模型结果、补充缺失参数和异步等待外部事件。

## 8.1 动态中断 interrupt

动态中断写在节点函数内部：

```python
from typing import TypedDict

from langgraph.checkpoint.memory import InMemorySaver
from langgraph.graph import END, START, StateGraph
from langgraph.types import Command, interrupt


class State(TypedDict):
    request: str
    approved: bool


def approval(state: State) -> dict:
    approved = interrupt(
        {
            "type": "approval",
            "question": "是否批准该操作？",
            "request": state["request"],
        }
    )
    return {"approved": bool(approved)}


builder = StateGraph(State)
builder.add_node("approval", approval)
builder.add_edge(START, "approval")
builder.add_edge("approval", END)
graph = builder.compile(checkpointer=InMemorySaver())

config = {"configurable": {"thread_id": "approval-1001"}}
paused = graph.invoke({"request": "退款 500 元"}, config=config)
print(paused["__interrupt__"])

resumed = graph.invoke(Command(resume=True), config=config)
print(resumed["approved"])
```

执行过程：

```text
节点调用 interrupt(payload)
-> 运行时保存检查点并返回 Interrupt
-> 应用把 payload 展示给审核者
-> 应用用同一 thread_id 传入 Command(resume=value)
-> 被中断节点从头重新执行
-> interrupt() 返回 resume value
-> 节点继续完成
```

`interrupt()` 的参数是给外部调用方的数据，应使用 JSON 可序列化的字符串、数字、布尔、列表或字典。

## 8.2 为什么不是 input()

`input()` 会阻塞当前 Python 进程，只适用于终端交互。`interrupt()` 会持久化任务并结束当前请求，几分钟甚至几天后，可以在另一个进程中恢复，更适合服务端工作流。

| `input()` | `interrupt()` |
| --- | --- |
| 阻塞当前进程 | 释放当前请求和计算资源 |
| 进程退出后无法恢复 | 通过 Checkpointer 跨进程恢复 |
| 只适合终端 | 适合 API、审批系统和消息队列 |

## 8.3 中断恢复的重要规则

### 节点会从头执行

恢复后不是从 `interrupt()` 下一行进行 Python 级续执行，而是重新运行整个节点。运行时会按顺序把已保存的 resume 值交回对应的 `interrupt()`。

因此，中断前的副作用必须满足以下之一：

- 移到 `interrupt()` 之后。
- 拆到独立节点。
- 使用业务幂等键，允许重复执行。

### 不要捕获 interrupt

底层通过特殊异常暂停图，不能用宽泛的 `try/except` 包住：

```python
# 错误：可能吞掉 GraphInterrupt
try:
    approved = interrupt("是否批准？")
except Exception:
    approved = False
```

### 中断顺序必须稳定

同一节点有多个 `interrupt()` 时，恢复值按调用顺序匹配。不要根据恢复前后可能变化的列表或条件动态改变中断数量和顺序。

### 恢复值必须校验

`resume` 来自外部调用方。节点收到后仍应校验类型、权限和业务约束，不能因为它来自审批界面就自动可信。

## 8.4 并行中断

并行节点可能同时产生多个 Interrupt。每个 Interrupt 都有自己的 `id`，恢复时可以传映射：

```python
resume_values = {
    interrupt_item.id: value,
    another_interrupt.id: another_value,
}

graph.invoke(Command(resume=resume_values), config=config)
```

应用层应保存 `thread_id`、Interrupt ID、审核人、审核时间和审核结果，避免把多个并行审批混淆。

## 8.5 审批节点设计

推荐把“申请审批”和“执行危险动作”拆开：

```text
prepare_action
-> approval_node: interrupt
-> route_by_approval
-> execute_action / rejected
```

审批前展示完整业务信息，而不是只展示模型生成的一句话：

- 操作类型和目标资源。
- 金额、数量等关键参数。
- 当前用户和权限范围。
- 幂等业务操作 ID。
- 风险说明和可撤销性。

批准后，执行节点仍要重新鉴权并校验状态，因为审批期间业务数据可能已经变化。

## 8.6 静态断点

静态断点在节点边界暂停，主要用于调试：

```python
graph = builder.compile(
    checkpointer=InMemorySaver(),
    interrupt_before=["execute"],
    interrupt_after=["prepare"],
)
```

也可以在调用时传入 `interrupt_before` / `interrupt_after`。恢复静态断点通常传 `None`：

```python
graph.invoke(None, config=config)
```

| 动态中断 | 静态断点 |
| --- | --- |
| 节点内部显式调用 `interrupt()` | 在节点执行前或执行后暂停 |
| 能携带业务审批数据 | 更偏开发和调试 |
| 用 `Command(resume=value)` 恢复 | 通常用 `invoke(None, config)` 继续 |
| 适合生产人工介入 | 不建议替代正式审批流程 |

## 8.7 检查状态

中断后可以查看：

```python
snapshot = graph.get_state(config)
print(snapshot.values)
print(snapshot.next)
print(snapshot.interrupts)
print(snapshot.tasks)
```

`values` 是中断前已提交的 State；中断节点尚未完成的返回值不会提前写入。

## 8.8 生产清单

1. 必须使用可持久化 Checkpointer。
2. `thread_id` 与当前用户、租户和业务任务绑定。
3. 审批接口需要鉴权、审计、防重放和过期时间。
4. 中断前副作用幂等，危险副作用尽量放到批准后的独立节点。
5. 恢复值执行 Schema 与业务校验。
6. 审批超时、拒绝和任务取消都有明确路径。
7. 部署升级时保证旧中断节点和 State Schema 仍可恢复。
