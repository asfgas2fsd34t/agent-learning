# 08 中间件

> 来源：`尚硅谷-08-中间件.pdf`。本章使用当前项目 LangChain 1.3 的中间件名称和参数。

## 学习目标

- 理解中间件在 Agent 执行图中的位置
- 掌握常用内置中间件的用途和边界
- 实现人工审核、敏感信息处理、调用限制和重试
- 使用 Node-style 与 Wrap-style Hook 自定义中间件
- 理解多个中间件的执行顺序

## 1. 什么是中间件

中间件是在 Agent 生命周期关键位置拦截、观察或修改执行过程的组件。

```text
用户输入
  -> before_agent
  -> before_model
  -> wrap_model_call(模型调用)
  -> after_model
  -> wrap_tool_call(工具调用，可能发生多次)
  -> ...模型和工具循环...
  -> after_agent
```

常见用途：

- 对话过长时自动摘要
- 工具执行前人工审批
- 检测和处理敏感信息
- 限制模型与工具调用次数
- 模型或工具临时失败时重试
- 动态筛选工具、切换模型或修改 Prompt
- 记录日志、耗时和错误

中间件不改变业务服务的最终责任。权限、资源归属、幂等和数据库事务仍必须由可信业务代码保证。

## 2. 中间件分类

### 2.1 按来源

```text
内置中间件：LangChain 已实现，配置后使用
自定义中间件：使用 Hook 装饰器或继承 AgentMiddleware
```

### 2.2 按执行形态

```text
Node-style Hook：在图中成为独立节点，读取 state 并返回状态更新
Wrap-style Hook：包裹一次模型或工具调用，可在调用前后执行逻辑
```

### 2.3 注册方式

```python
from langchain.agents import create_agent

agent = create_agent(
    model=model,
    tools=tools,
    middleware=[middleware_a, middleware_b],
)
```

顺序会影响执行结果，第 6 节会详细说明。

## 3. 常用内置中间件

### 3.1 `SummarizationMiddleware`

当历史消息接近限制时，把较早对话压缩为摘要，保留近期消息：

```python
from langchain.agents.middleware import SummarizationMiddleware

summary = SummarizationMiddleware(
    model=model,
    trigger=("tokens", 8_000),
    keep=("messages", 20),
)
```

关键参数：

| 参数 | 作用 |
|---|---|
| `model` | 生成摘要的模型 |
| `trigger` | 按 Token、消息数或上下文比例触发 |
| `keep` | 摘要后保留最近多少消息或比例 |
| `token_counter` | Token 统计函数 |
| `summary_prompt` | 自定义摘要要求 |
| `trim_tokens_to_summarize` | 摘要模型本次接收的历史上限 |

摘要是有损压缩，可能遗漏细节。订单号、审批状态、工具结果和用户明确约束等关键数据更适合放入结构化 State，而不是只依赖自然语言摘要。

### 3.2 `HumanInTheLoopMiddleware`

它在指定工具执行前中断 Agent，等待人工决定：

```python
from langchain.agents.middleware import HumanInTheLoopMiddleware
from langgraph.checkpoint.memory import InMemorySaver

agent = create_agent(
    model=model,
    tools=[query_order, refund_order],
    middleware=[
        HumanInTheLoopMiddleware(
            interrupt_on={
                "query_order": False,
                "refund_order": {
                    "allowed_decisions": ["approve", "edit", "reject"],
                },
            }
        )
    ],
    checkpointer=InMemorySaver(),
)
```

调用时必须使用稳定的 `thread_id`：

```python
config = {"configurable": {"thread_id": "refund-task-001"}}

result = agent.invoke(
    {"messages": [{"role": "user", "content": "退掉订单 A100"}]},
    config=config,
)
```

中断结果中会包含待审核的工具名称、参数和说明。审核后通过 `Command(resume=...)` 恢复同一线程：

```python
from langgraph.types import Command

result = agent.invoke(
    Command(
        resume={
            "decisions": [
                {"type": "approve"},
            ]
        }
    ),
    config=config,
)
```

可选决策：

| 决策 | 作用 |
|---|---|
| `approve` | 按原参数执行 |
| `edit` | 审核人修改工具名称或参数后执行 |
| `reject` | 拒绝执行，并把原因反馈给 Agent |

生产环境要求：

- 必须配置持久化 Checkpointer，否则进程结束后无法可靠恢复
- 审批接口必须鉴权，记录审批人、时间、原参数和决策
- 审批通过后仍要做权限、状态和幂等校验
- 中断时不应占用工作线程等待
- 前端展示应只暴露必要字段，隐藏密钥和内部参数

#### 审批记录的最小字段

一次审批不能只保存“已同意”。至少要能回答谁申请、审批了什么、最终执行了什么：

```text
approval_id
thread_id / checkpoint_id
tenant_id / requester_user_id
tool_name / tool_version
original_args_snapshot / args_hash
risk_level
allowed_decisions
status: pending / approved / edited / rejected / expired / executed
approver_user_id
decision_reason
created_at / decided_at / expires_at
operation_id / idempotency_key
```

关键原则：

- 审批页面展示的参数必须与记录中的快照一致
- `edit` 后保存修改前后参数；风险显著变化时重新审批
- 审批有有效期，超时后不能继续执行旧操作
- 审批通过不等于业务一定可执行，执行前重新检查权限和资源状态
- 实际执行结果要回写审批记录，并关联业务操作 ID

```text
Agent 产生候选动作
-> 参数标准化并创建审批记录
-> Checkpointer 保存中断位置
-> 审批系统写入决定
-> 使用相同 thread_id 恢复
-> 校验审批快照和当前动作一致
-> 再次执行业务校验
-> 使用幂等键执行并记录结果
```

### 3.3 `PIIMiddleware`

用于识别和处理个人敏感信息：

```python
from langchain.agents.middleware import PIIMiddleware

middleware = PIIMiddleware(
    "email",
    strategy="redact",
    apply_to_input=True,
    apply_to_output=True,
    apply_to_tool_results=True,
)
```

内置类型包括邮箱、信用卡、IP、MAC 地址和 URL；也可以传自定义类型与检测器。

处理策略：

| 策略 | 结果 |
|---|---|
| `block` | 检测到后阻止处理 |
| `redact` | 替换为固定脱敏标记 |
| `mask` | 保留部分字符，其余掩码 |
| `hash` | 替换为哈希值，便于关联但不可直接恢复 |

PII 检测不可能绝对完整。日志、数据库、Trace、模型输入和工具结果都需要独立的数据治理策略。

### 3.4 `TodoListMiddleware`

为 Agent 增加 `write_todos` 工具和任务列表状态，让复杂任务能够显式规划与更新进度：

```python
from langchain.agents.middleware import TodoListMiddleware

agent = create_agent(
    model=model,
    tools=tools,
    middleware=[TodoListMiddleware()],
)
```

执行逻辑：

```text
中间件注入 write_todos 工具和使用说明
-> 模型判断任务是否复杂
-> 创建待办列表
-> 执行一步
-> 更新该步状态
-> 根据结果修订后续计划
```

Todo 列表是显式状态，不等于模型真的拥有可靠的长期规划能力。简单任务不应强制使用，否则会增加模型调用和 Token 消耗。

## 4. 其他内置中间件

### 4.1 调用限制

#### `ModelCallLimitMiddleware`

```python
from langchain.agents.middleware import ModelCallLimitMiddleware

limit_models = ModelCallLimitMiddleware(
    run_limit=6,
    thread_limit=20,
    exit_behavior="end",
)
```

- `run_limit`：本次 Agent 运行最多调用模型多少次
- `thread_limit`：同一线程累计最多调用多少次
- `exit_behavior`：超过限制时结束或抛错

#### `ToolCallLimitMiddleware`

```python
from langchain.agents.middleware import ToolCallLimitMiddleware

limit_refunds = ToolCallLimitMiddleware(
    tool_name="refund_order",
    run_limit=1,
    thread_limit=2,
    exit_behavior="error",
)
```

可以限制全部工具，也可以只限制某个工具。调用上限能降低循环风险，但不能代替退款业务的幂等控制。

### 4.2 模型降级

#### `ModelFallbackMiddleware`

```python
from langchain.agents.middleware import ModelFallbackMiddleware

fallback = ModelFallbackMiddleware(
    primary_model,
    backup_model,
)
```

主模型失败时尝试后备模型。需要注意：

- 两个模型的 Tool Calling 和 Structured Output 能力可能不同
- 成本、延迟和上下文窗口可能变化
- 参数或鉴权错误不适合盲目 fallback

### 4.3 工具筛选

#### `LLMToolSelectorMiddleware`

当 Agent 总工具很多时，先由一个模型筛选与当前请求最相关的子集：

```python
from langchain.agents.middleware import LLMToolSelectorMiddleware

selector = LLMToolSelectorMiddleware(
    model=small_model,
    max_tools=5,
    always_include=["get_current_user"],
)
```

它降低主模型的工具选择负担，但会增加一次模型调用，而且筛选错误可能让必要工具不可见。权限过滤应先于语义筛选，不能让选择模型看到用户无权使用的工具。

### 4.4 工具重试

#### `ToolRetryMiddleware`

```python
from langchain.agents.middleware import ToolRetryMiddleware

retry_tools = ToolRetryMiddleware(
    max_retries=2,
    tools=["search_news"],
    retry_on=(TimeoutError, ConnectionError),
    initial_delay=1.0,
    backoff_factor=2.0,
    max_delay=10.0,
    jitter=True,
    on_failure="continue",
)
```

只重试临时性错误。参数错误、权限拒绝、余额不足等确定性失败不应重试。写工具必须先实现业务幂等，才可以安全重试。

### 4.5 模型重试

#### `ModelRetryMiddleware`

```python
from langchain.agents.middleware import ModelRetryMiddleware

retry_model = ModelRetryMiddleware(
    max_retries=2,
    retry_on=(TimeoutError, ConnectionError),
    initial_delay=1.0,
    backoff_factor=2.0,
    jitter=True,
)
```

它重试的是模型 API 调用，不是让模型重新规划一次业务任务。总耗时应受外层请求截止时间约束。

### 4.6 工具模拟

#### `LLMToolEmulator`

使用模型模拟指定工具的返回：

```python
from langchain.agents.middleware import LLMToolEmulator

emulator = LLMToolEmulator(
    tools=["get_weather"],
    model=small_model,
)
```

适合原型、演示或缺少外部依赖的开发环境。它不能用于验证真实接口、权限、幂等、延迟和错误处理，也不应在生产中把模拟结果当作真实事实。

### 4.7 上下文清理

#### `ContextEditingMiddleware`

工具返回大量内容后，历史中的旧工具结果会持续占用上下文。该中间件可以按编辑策略清除或缩减旧工具结果：

```python
from langchain.agents.middleware import (
    ClearToolUsesEdit,
    ContextEditingMiddleware,
)

context_editor = ContextEditingMiddleware(
    edits=[ClearToolUsesEdit(trigger=10_000)],
    token_count_method="approximate",
)
```

不要清理仍影响后续决策的关键 Observation。结构化业务状态应从消息文本中独立保存。

### 4.8 文件搜索

#### `FilesystemFileSearchMiddleware`

```python
from langchain.agents.middleware import FilesystemFileSearchMiddleware

file_search = FilesystemFileSearchMiddleware(
    root_path="./workspace",
    use_ripgrep=True,
    max_file_size_mb=10,
)
```

它给 Agent 提供受根目录约束的文件搜索能力。必须固定 `root_path`，限制文件大小，并避免把密钥、系统目录和其他租户文件纳入范围。

### 4.9 Shell 工具

#### `ShellToolMiddleware`

```python
from langchain.agents.middleware import ShellToolMiddleware

shell = ShellToolMiddleware(
    workspace_root="./workspace",
    execution_policy=execution_policy,
)
```

Shell 是高风险能力，生产中至少需要：

- 沙箱或隔离容器
- 工作目录限制
- 命令允许/拒绝策略
- 时间、CPU、内存和输出大小限制
- 环境变量与密钥脱敏
- 网络访问策略
- 审计日志和人工审批

仅靠 System Prompt 禁止危险命令不构成安全控制。

### 4.10 Filesystem 与 Subagent

课件还介绍了更完整的 Filesystem 和 Subagent 中间件，用于文件读写编辑和把子任务委派给子 Agent。这些能力常来自 Deep Agents 等扩展包，不一定由当前 `langchain.agents.middleware` 直接导出。

```text
Filesystem：受控读、写、编辑、列目录
Subagent：把独立子任务交给隔离的 Agent 执行
```

使用前必须核对所安装扩展包的版本和导入路径。多 Agent 的架构设计不在当前学习阶段展开。

## 5. 自定义中间件

## 5.1 六个核心 Hook

| Hook | 类型 | 典型用途 |
|---|---|---|
| `before_agent` | Node-style | 初始化状态、入口校验 |
| `before_model` | Node-style | 消息裁剪、调用前日志、路由 |
| `after_model` | Node-style | 检查模型输出、状态更新 |
| `after_agent` | Node-style | 最终审计、结果后处理 |
| `wrap_model_call` | Wrap-style | 模型重试、缓存、动态模型/Prompt |
| `wrap_tool_call` | Wrap-style | 工具重试、监控、参数控制 |

同步 Agent 使用同步 Hook；异步 Agent 对应实现异步版本。不要在异步 Hook 中执行长时间阻塞 I/O。

## 5.2 Node-style：装饰器写法

```python
from typing import Any

from langchain.agents.middleware import AgentState, before_model
from langgraph.runtime import Runtime


@before_model
def log_before_model(
    state: AgentState,
    runtime: Runtime,
) -> dict[str, Any] | None:
    print(f"模型调用前消息数：{len(state['messages'])}")
    return None
```

返回 `None` 表示不更新状态；返回字典表示把字段合并进 State：

```python
return {"audit_status": "checked"}
```

某些 Hook 可以通过返回 `jump_to` 改变执行路径。装饰器定义时必须用 `can_jump_to` 声明可能目的地，让图在编译时知道合法跳转：

```python
@before_model(can_jump_to=["end"])
def stop_if_blocked(state: AgentState, runtime: Runtime):
    if state.get("blocked"):
        return {"jump_to": "end"}
    return None
```

## 5.3 Node-style：类写法

```python
from langchain.agents.middleware import AgentMiddleware, AgentState
from langgraph.runtime import Runtime


class AuditMiddleware(AgentMiddleware):
    def before_model(self, state: AgentState, runtime: Runtime):
        print(f"模型调用前消息数：{len(state['messages'])}")
        return None

    def after_model(self, state: AgentState, runtime: Runtime):
        print(f"模型调用后消息数：{len(state['messages'])}")
        return None
```

注册时要实例化：

```python
middleware=[AuditMiddleware()]
```

## 5.4 Wrap-style：模型调用

Wrap Hook 接收 `handler`。调用 `handler(request)` 才会真正进入下一个中间件或模型：

```python
from collections.abc import Callable

from langchain.agents.middleware import (
    ModelRequest,
    ModelResponse,
    wrap_model_call,
)


@wrap_model_call
def monitor_model(
    request: ModelRequest,
    handler: Callable[[ModelRequest], ModelResponse],
) -> ModelResponse:
    print("调用模型前")
    response = handler(request)
    print("调用模型后")
    return response
```

可以使用 `request.override(...)` 创建修改后的请求：

```python
modified = request.override(model=backup_model)
return handler(modified)
```

适用场景：

- 按状态动态切换模型
- 修改 System Prompt 或可用工具
- 模型响应缓存
- 限定错误类型的重试
- 记录延迟、Token 和错误

## 5.5 Wrap-style：工具调用

```python
from collections.abc import Callable

from langchain.agents.middleware import ToolCallRequest, wrap_tool_call
from langchain_core.messages import ToolMessage
from langgraph.types import Command


@wrap_tool_call
def monitor_tool(
    request: ToolCallRequest,
    handler: Callable[[ToolCallRequest], ToolMessage | Command],
) -> ToolMessage | Command:
    tool_name = request.tool_call["name"]
    print(f"开始执行：{tool_name}")
    result = handler(request)
    print(f"执行完成：{tool_name}")
    return result
```

`request.tool_call` 中的名称和参数来自模型，不可信。修改参数前应复制请求或使用框架提供的替换方式，避免原地修改导致日志、审批记录和实际执行参数不一致。

## 5.6 装饰器还是类

```text
只有一个简单 Hook -> 装饰器
多个 Hook 共享配置或状态 -> AgentMiddleware 子类
需要构造参数和可复用实例 -> 类
快速原型、逻辑很短 -> 装饰器
```

装饰器底层也会创建 `AgentMiddleware` 子类实例，两种方式接入的是同一套生命周期。

## 6. 多个中间件的执行顺序

假设注册顺序为：

```python
middleware=[A, B, C]
```

### 6.1 Node-style Hook

```text
before_agent / before_model：A -> B -> C
after_model / after_agent：C -> B -> A
```

### 6.2 Wrap-style Hook

先注册的中间件在最外层，形成洋葱结构：

```text
A before
  B before
    C before
      model/tool
    C after
  B after
A after
```

因此顺序不是排版问题，而是行为的一部分。例如缓存放在重试外层与放在重试内层，会产生不同的命中和异常行为。

## 7. 推荐组合

一个受控的业务 Agent 可以从以下顺序开始：

```python
middleware = [
    PIIMiddleware("email", strategy="redact"),
    ModelCallLimitMiddleware(run_limit=6),
    ToolCallLimitMiddleware(run_limit=8),
    SummarizationMiddleware(model=summary_model),
    HumanInTheLoopMiddleware(
        interrupt_on={"refund_order": True},
    ),
    ToolRetryMiddleware(
        tools=["query_order"],
        retry_on=(TimeoutError,),
    ),
]
```

这只是起点，实际顺序需要通过测试验证：

- 敏感信息是在记录日志前还是后处理
- 调用限制是否统计重试次数
- 审批发生在参数标准化前还是后
- 缓存是否允许绕过模型调用
- 工具失败是否应该反馈模型继续规划

## 8. 生产检查清单

- 中间件顺序有自动化测试
- 所有重试都有错误白名单、退避和次数上限
- 写工具具有业务幂等，不依赖调用次数限制
- 高风险工具配置持久化人工审核
- Checkpointer 支持进程重启后恢复
- PII 同时覆盖输入、输出、工具结果、日志和 Trace
- Shell 和文件工具有沙箱与目录边界
- 超限、拒绝、失败和未知状态都有稳定错误协议
- 日志记录模型、工具、耗时、Token、决策和脱敏参数
- 不向用户展示隐藏推理、内部异常栈和敏感上下文

## 总结

```text
Summarization：压缩长历史
HumanInTheLoop：工具执行前中断并审批
PII：检测和处理敏感信息
TodoList：显式规划与进度状态
CallLimit：限制模型和工具循环
Retry / Fallback：处理临时失败和降级
ToolSelector：动态缩小工具集合
ContextEditing：清理旧工具结果
Node-style：图节点式前后处理
Wrap-style：洋葱式包裹真实调用
```

中间件是 Agent 工程控制层，适合统一实施观察、限制和编排；真正的数据安全和业务一致性仍由后端服务兜底。
